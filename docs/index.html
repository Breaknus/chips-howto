0. Подготовка и постановка цели

Что делаем:

  1. Фиксируем глубину исследования: полный транзисторный нетлист (6502 в breaks); уровень стандартных ячеек (SEGA/Yamaha в SEGAChips — «реверс таких чипов похож на дизассемблирование программ»); вентильный уровень (ula, mappers); обзор большой SoC (psxcpu, dmgcpu).
  2. Собираем референсы: service manual, блок-схемы из книжек, патенты, чужие реверсы (msinger/Gekkio в dmgcpu, zxdesign.info и патент EP0107687B1 в ula, документация LSI Logic CoreWare в psxcpu).
  3. Выписываем терминологию до начала: latch/DFF/FF/DLatch (dmgcpu), CPU/PPU, RAM/VRAM/WRAM/PRG/CHR (mappers). Споры о терминах, начатые после начала трассировки, съедают недели.
Шишка: отсутствие референсов приводит к «самоназванию» сигналов и невозможности свериться later. В psxcpu референсом сознательно выбран block diagram из service manual PU-22, где CPU подключён наиболее полно.
Результат: stated goal · reference list · terminology dictionary
Результат шага: поставленная цель, список референсов, словарь терминов.

1. Добыча чипа и датасетов

  1. Ищем донорскую плату нужной ревизии. Ревизию фиксируем сразу: маркировка корпуса, код ревизии на кристалле (tattoo), дата-код. Пример psxcpu: tattoo 90048 на кристалле соответствует маркировке L9A0048; разные ревизии могут отличаться разводкой M1/M2 настолько, что «перенести трассировку» нельзя — только заново.
  2. Сначала ищем готовые датасеты: visual6502, siliconpr0n, расшаренные GDrive-папки (breaks, SEGAChips, mappers). Ремесленник не переснимает то, что уже снято.
  3. Для серий чипов строим таблицу соответствия OEM-номеров и номерам производителя (chips.md в SEGAChips: YM7101 = 315-5313, клоны TA-06/SE-93...). Это карта всей экосистемы клониров.
  4. Выбираем Master Dataset — эталонное изображение, по которому будет строиться нетлист; остальные датасеты — вспомогательные.
Шишка: чип «не той» ревизии обнуляет недели работы. psxcpu: первые SCPH-1000 содержали старую архитектуру (3 слоя металла), а исследуют 90048; новые ревизии «пересобраны» из верилога — сверять трассировку между ними бессмысленно.
Результат: чип или чужой датасет, зафиксированная ревизия, план съёмки.

2. Распаковка (декапсуляция)

Подробно — в methods.md.

  1. Термический способ (ACID FREE): газовая горелка + плоскогубцы + ковырялка. Жарим кусок корпуса на улице до «готовности» — пока вместо чёрного пластика не останется серый пепел; затем аккуратно раздробляем и извлекаем кристалл.
  2. Очистка: чистый ацетон + деревянная зубочистка — дерево не царапает верхний металл, но снимает пластик и грязь.
  3. HF-путь (hf.md): травление стекла/кремния для оптической проявки областей легирования; доступны «мази» типа Armour Etch. Миллилитры, а не литры — и полная СБ.
Шишки (жизненные): дым горелого пластика вызывает отёк лёгких — только улица/вытяжка; ацетон — канцероген; HF связывает кальций, «кости рассыпаются», работаете в напальчниках и строительной маске; не смотреть в окуляры металлографического микроскопа подолгу — свет отражается от чипа прямо в сетчатку.
Результат: чистый кристалл на предметном стекле.

3. Съёмка датасета

  1. Металлографический микроскоп (дешёвый китайский AmScope отлично работает) + камера.
  2. Слайды снимаются равномерной сеткой «змейкой» с перекрытием 5–20% — иначе сшивка не сойдётся.
  3. Моторизованный столик + утилита автофокуса и автосъёмки. Классическая травма: после 300 слайдов ударили пяткой по столу — чип сдвинулся, весь прогон насмарку.
  4. Каждый delayering-проход — отдельный «лаг»: lap1, lap2, M1, M2... (psxcpu снимал M1 трижды: 20x-прогон оказался «практически бесполезен», 50x — пригоден).
  5. Фокус — компромисс: «M2 good focus» теряет M1 сквозь металл, «bad focus» просвечивает M1. Снимают оба варианта.
Шишки из psxcpu: датасеты с «кучей мусора» (куски проводов, грязь после кислотного травления) всё же пригодны — информацию извлечь можно; а вот пропуск части чипа из-за спешки («правые три ряда сточили до мяса») = дыры в нетлисте навсегда.
Результат: наборы слайдов 0001.jpg ... NNNN.jpg на каждый слой.

4. Сшивка — Master Dataset

  1. Fiji: Plugins → Stitching → Grid/Collection stitching.
  2. Шаблон имён слайдов {iiii}.jpg, порядок «змейкой» (сверху-вниз или снизу-вверх — как снимали), Tile overlap подбирается экспериментально (автор methods.md ставит 25 почти всегда; docs рекомендуют 5–20).
  3. Непонятные настройки лучше не трогать. После Run — «магия» и единая картинка.
  4. Fiji не сошёл (плохое/неравномерное перекрытие) → Hugin, но это больше ручного труда.
  5. Для топологии master часто уменьшают (ula: исходник в 4 раза → ZX_ULA_sm.jpg) — разрешение для трассировки не нужно, а работать легче.
Шишка: если автоматическая сшивка не сходится, не «тяните» её силой — проверьте постоянство перекрытия и масштаба съёмки; переделка прогона дешевле ручной подгонки в Hugin.
Результат: единое Master-изображение каждого слоя.

5. Работа со слоями (delayering)

  1. Чип приклеивается клеем «Момент» к предметному стеклу с «бугорками» по краями — иначе при полировке улетит к краю стекла.
  2. Дремель + паста ГОИ: сеансы полировки по 5–10 секунд, затем контроль под микроскопом и пересъёмка. С опытом снимаются слои 50–100 нм — достаточно для старых чипов.
  3. Слои складируются раздельно и навсегда: poly / active / M1 / M2... (lap1-4 в dmgcpu, M1 Lap1/Lap2 в psxcpu).
  4. Для чипов с одним слоем металла (ULA: бипроцесс, один m1 — см. topo.md) делиеровка может не потребоваться вовсе: хватает poly + M1.
  5. HF помогает проявить легированные области оптически (hf.md), когда полировки недостаточно.
Шишки: оксиды хрома из пасты ГОИ — мутагены, берегите лёгкие и глаза; слишком усердная полировка съедает слой («lapping disaster» правого края в psxcpu) — лучше лишний короткий сеанс, чем один длинный.
Результат: полный набор изображений всех слоёв кристалла.

6. Библиотека стандартных ячеек

  1. Определяем «стиль» чипа: почти всё после 70-х набрано стандартными ячейками; у УLA (биполярный, 2 типа ячеек: логические not/nor + периферийные) библиотека вырожденная — достаточно векторизовать базовые элементы (ulabase.v).
  2. Patterns сопоставляет библиотеку ячеек с мастер-изображением и экспортирует координаты+имена в XML/TXT для Deroute.
  3. Каталог документируется в cells.md фото каждой ячейки: Yamaha YM_Cells/YM6_Cells («двухэтажные» ячейки) в SEGAChips, CoreWare-ячейки в psxcpu, cells.md в dmgcpu и mappers (там же — разбор по names: dec→dec4, dec2→dcd2 — именование сразу с префиксом функции).
  4. Разрядность/ориентация ячейки фиксируются: Patterns показывает метку по ориентации ячейки; ряды ячеек сшиваются в «колбаски» (row_m1 в psxcpu) для удобства навигации.
Шишка: «мусорные» ячейки-пустышки (dummies, fillers) тоже существуют — их распознание и исключение экономит время (psxcpu FILLER cell; ula: peripheral-инверторы не включаются в основной нетлист, но один инвертор из периферийной ячейки всё же задействован разработчиками в /AE — не «удаляйте всё подряд»).
Результат: cells.md + patterns_db.

7. Получение нетлиста (Deroute)

  1. Порядок трассировки, отработанный на dmgcpu/psxcpu/mappers: pads/ports → top-level → слой за слоем (M1, M2...) → декомпозиция на модули (ports.md → netlist/m1.xmlz → BG/FSM/MUX... в VDP SEGAChips).
  2. Ручная прорисовка всех проводов физически невозможна — применяется полуавтоматический метод (psxcpu netlist/method.png): рисуются только крайние vias провода, остальное скрипт собирает сам.
  3. «Собачьи ноги» (dog-leg): на пресет кладётся только один сегмент-заплатка; промежуточные vias помечаются x, чтобы восстановление провода на них не обрывалось.
  4. Параметры Deroute фиксируются в начале и не меняются: psxcpu — Lambda: 6.0, Vias Size: 2, Wire Size: 3.
  5. Сцена сохраняется в XML (.xmlz) — это и есть «база» нетлиста.
Шишки: Lambda задаётся один раз — переопределение масштаба ломает уже разложенные сущности; power/ground rails дают ложные warnings (Deroute #106 — фикс); bidir-порты не считать floaters (#88). Проверяйте нетлист счётчиками, а не «на глаз».
Результат: нетлист (XML) — соединение модулей проводами.

8. Экспорт в Verilog

  1. Deroute выгружает нетлист сразу в Verilog — «die-perfect»: цель повторить оригинал, а не синтезировать красивое (Synthesizable — вообще другая задача).
  2. Проверяем, что код хотя бы компилируется (Icarus) — кривые порты всплывают сразу (fix в dmgcpu: «Cell not:g2 port x not connected fixed»).
  3. Флоатеры/шина: добавляем bus keeper там, где в оригинале он физически есть (buskeeper на внутренней шине DL, dmgcpu — без него сим «зависает» на чтении меняющегося STAT).
  4. Именование verilog-сущностей ведём из Deroute-нетлиста, не «с чистого листа».
Шишка: HDL vs нетлист расходятся семантикой примитивов (2-input NOR в модели vs библиотека ячеек) — сосуществование двух миров надо проверять структурно, а не полагаться на «компилируется, значит верно» (отчёт HDL-vs-netlist в ula).
Результат: chip.v с сетями оригинала, компилируемый стенд.

9. Визуализация в EDA

  1. Загружаем die-perfect verilog в Xilinx PlanAhead — он сам рисует схему (ula: «грузим верилог, она сама рисует схему»; dmgcpu: «Design extracted from PlanAhead»).
  2. Полученную схему используем как «воронку» анализа: плохое место на схеме быстрее ищется картинкой, чем тысячей строк verilog.
  3. Схемы модулей сохраняем как артефакты исследования (png) — они же идут в wiki/docs.
Шишка: EDA-схема плоская и шумная — не пытайтесь «понять всё сразу»; сначала декомпозиция (шаг 10), потом вдумчивое чтение.
Результат: читаемая схема для анализа.

10. Анализ и декомпозиция

  1. Дробим плоский нетлист на функциональные блоки и рисуем их прямо на изображении: annotated map УLA, блоки VDP (BGLogic/FSM/MUX/CRAM...), блок-схема PSX CPU, SoC DMG.
  2. Именуем сигналы человеческими именами, но пакетами и без фанатизма: «Renaming a signal does not make it work differently» (dmgcpu). Переименование = атомарный проход wiki+HDL+tran разом (breaks: «PPU Signal rename Wave1» — три PR подряд в один день).
  3. Таблицы сигналов: имя → откуда → куда → описание. Эталон — clkgen.md в dmgcpu; по ним же сверяют симуляцию.
  4. Waves: типовые временные диаграммы ключевых узлов (waves.png в mappers, ulasim.py → ula_waves.vcd в ula, waves-страницы wiki breaks).
  5. Советские чипы — тот же цикл: даташит → фото кристалла → Logisim-модель (vi53.circ) → Verilog (wr_edge.v) → PDF-отчёт (SovietChips).
Шишка: переименование «по одному сигналу в час» рождает расхождения между HDL и wiki; и наоборот — раннее именование «на глаз» без таблицы приводит к ложным From/Where To, которые потом пришлось переписывать (dmgcpu #330/#363).
Результат: разбор модулей, словари сигналов, волновые диаграммы.

11. Верификация

  1. Тестбенчи: Icarus Verilog + GTKWave (ula.gtkw), logisim-модели ячеек (mappers), «ppu standalone testbench» в breaks.
  2. Структурная сверка HDL vs нетлист: все гейты раскладываются идентично, иначе — ищем где (отчёт issue #2 в ula; там же честный вывод: модель остаётся X из-за различий NOR-семантики).
  3. Кросс-чек с сообществом: msinger/Gekkio (dmgcpu), zxdesign (ula), nesdev/forums (breaks, mappers). Расхождения — в issues, не «в комментариях в голове».
  4. Динамические corner cases: чтение регистра во время его изменения (STAT AND-эффект в mooneyes-тестах, dmgcpu), автозагрузка ROM/параметров в рантайме (+parameter=value для параллельных прогонов симуляции).
  5. Помечайте unverified:claim из техотчёта про DMC+OAM в breaks живёт с явным «unverified» — честность важнее красоты.
Шишка: со-симуляция «в лоб» может зависнуть (Icarus hangs в ula) — готовьте отдельный flow сравнения, а не один большой стенд.
Результат: подтверждённый нетлист + список открытых вопросов.

12. Документация и итерации

  1. Wiki с прогресс-таблицей по каждому блоку: Topology / Ports / Cells / Netlist / Verilog / Verification — как в dmgcpu. Таблица превращает хаос в план.
  2. Двуязычность: RU+EN; если раздела нет на английском — «можно спокойно использовать DeepL» (SEGAChips, ula).
  3. Конспект в книги PDF с релизами-ревизиями (breaks: 6502/APU/PPU books) — то, что можно распечатать, переживает любой хостинг.
  4. Живые инструменты: Deroute и Patterns допиливаются по запросам исследований (minimap, bulk rename, traverse black list, collaboration/CollabMCP).
  5. Переиспользование: CMOS Z80 из SEGAChips — «для других систем»; MBC1 из mappers — референс PPU в dmgcpu и наоборот. Каждое исследование должно кормить следующее.
Шишки: LLM-сгенерированный текст («boilerplate openers») правят до деловитого стиля, иначе wiki читают через силу (dmgcpu #363); секции из разных источников (сайт/форум/старая wiki) неизбежно дублируются — «всё встанет на места со временем» (psxcpu), но дубли надо помечать сразу.
